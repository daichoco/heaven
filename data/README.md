# Data files

Tabular datasets use JSON Lines (`.jsonl`): one JSON object per record. Read and write them with `src/data_store.py`, which validates expected columns and replaces files atomically.

- `cityheaven_shop_prices.json`: independent public shop-price cache, version 1 `shops[normalized CityHeaven shop URL]`. Written only by `src/shop_prices.py`, never by HTML generation, ranking, image collection or schedule collection. Each entry stores `status`, `reason`, `source_url`, `checked_at`, `source_kind` (`http` / `saved_html`), optional saved-file `observed_at` (file timestamp, not guaranteed page freshness), all observed duration/price candidates with section/name/conditions/eligibility, the selected ordinary course and its unrounded `yen_per_60`, tax state, and separate additional-fee evidence. No identifying profile data or full saved page is stored. Commit intentional public price snapshots with generated HTML; never add schedule/image caches just because a price was collected.
  The parser supports the observed `#shopcontent table.feesmart` structure, not a per-shop title whitelist. It records every paired duration/name and price row, table index, section/tab context and notes before deciding. Unicode-width normalization, decorative headings and narrow recommendation suffixes are accepted while raw labels remain stored. Ordinary/basic semantics plus time/single-price rows can establish one base system; generic price/system/course headings require at least two different durations and no unresolved competing system. A headingless table also requires an observed DOM table boundary. Legacy caches without `table_index` cannot establish headingless boundaries; duplicate-duration legacy groups stay on hold rather than reconstructing tables by guesswork. `table_decisions` and per-row roles/reasons retain the acceptance/exclusion/hold evidence (`decision_version: 2`).
  Specials/extensions/introductory/coupon/limited/points rows and tables are excluded at their own scope, including promotion context inherited from a section's tab. Separate nomination/transport/service/entry/time-of-day surcharge notes and reservation links do not invalidate a clearly ordinary base table. Notes remain visible and are never silently added. Promotion-qualified tables, unseparated time/rank conditions, unknown product names, competing base systems, ranges, mixed base/discount/total amounts and conflicting tax labels remain on hold, not minimized. A contradiction at any duration prevents selecting even an apparently clear 90-minute row. Ordinary 90 minutes takes precedence; otherwise nearest duration, longer duration at equal distance. `yen_per_60 = base_yen * 60 / minutes`; filtering uses the unrounded result, display rounds to the nearest yen. It is not an actual 60-minute offer or payable total. Taxes are not silently added; tax inclusion/exclusion/unknown and separate nomination/transport/other fees remain visible.
  Collection is serial and deduplicated per shop, with a one-second pause between shops, 20-second request timeout and 2MiB response limit. Redirects are not followed; HTTP 401/403/429, 404/410 and transport errors retain distinct states. There is no age/login/access-control bypass, AI, API, automatic refresh or automatic all-shop collection. Existing entries (including failures) stay cached unless `--refresh` is explicitly requested. Each result is atomically saved without dropping other shops; partial failures return exit code 1.
  Examples: 愛らぶ名古屋本店 ordinary 90 minutes ¥27,000 → ¥18,000/60 minutes (inclusive tax); alamode 90 minutes ¥14,000 → ¥9,333.33; alicejogakuin_n 100 minutes ¥29,000 → ¥17,400; alicejogakuin_nayabashi 90 minutes ¥27,000 → ¥18,000. The latter three retain unknown tax and separate fee conditions. e-com's decorated `■基本コース` now selects 90 minutes ¥27,000 → ¥18,000; its two event/time-slot discount tables remain excluded. av-nayabashi's hours heading plus mixed base/entry/total amounts and beppin-c's time-slot heading plus limited/group-discount notes remain unresolved; raw amounts alone do not establish a safe base system. でりどす岡崎 / リージェントクラブ貴公子 have no extracted candidates, not proof that no prices exist.
  The user's completed collection supplied 283 shop records, 2,083 candidate rows and 597 saved table/context groups. Offline re-evaluation made 30 previously unknown shops usable: `ok 18 / unknown 225 / redirect 40` → `ok 48 / unknown 195 / redirect 40`; all 18 prior selected durations and base/converted amounts are unchanged. The remaining unknowns include 149 with candidates and 46 without extracted candidates. The 48 usable-shop subset has min/median/max ¥8,000/¥17,000/¥39,000 per 60 minutes; band counts are 4 / 8 / 29 / 5 / 0 / 2 in ascending known-price bands. This subset is **not** representative of unresolved shops or a complete regional market. This update issued no HTTP requests. No luxury/cheap labels are inferred; NS's explicit 高級 label is unchanged.
  `--reprocess-cache PATH --shop-url URL --refresh` explicitly re-evaluates selected candidate-bearing `unknown` entries. `--reprocess-all` explicitly audits all saved `ok` and `unknown` candidates with the same selector (no HTTP); an optional `--reprocess-cache PATH` reads and merges another snapshot without modifying its source. Original raw evidence, source URL, `checked_at`, tax and fee evidence remain; `reprocessed_at` is analysis time, not a page visit. Newer observations take precedence, while different older evidence is retained with source digests. Same-time contradictory evidence stays unselected, never silently overwritten. Snapshot input hashes are recorded, and a changed destination or source aborts saving; run after collection finishes. Missing timezones or invalid input fail explicitly. Missing/ambiguous evidence stays unknown, and exit code 1 means unresolved statuses remain. No 404/410, restricted, error or redirect record is reclassified. HTML generation never initiates re-evaluation.

- `cityheaven_weekly_images.json`: image-only cache automatically written during normal `generate_weekly_schedule_report.py` generation, using the existing NS profile-image helper's URL-keyed schema (`image_url`, `status`, `checked_at`, optional shop metadata). Only missing images in S profiles or people with saved schedules in the current window are considered; `--include-a` includes uncollected A profiles too. Existing image URLs are never re-fetched. There is no default person-count limit; `--image-limit N` optionally limits work, and the existing 120-second time budget remains. Unprocessed/failed missing images are reported with nonzero exit, not silently considered complete. Error/no-image retry waits seven days, and 404/410 is not retried. Normal generation never rewrites schedule snapshots. Use `--offline` for no network or cache writes; `--collect-images` remains a compatibility option. Generation also reuses NS's existing image cache and calendar HTML. New schedule snapshots may contain an optional `image: {status, image_url}` captured from the same profile response; older snapshots without this key remain valid.

- `cityheaven_weekly_schedules.json`: targeted public CityHeaven schedule snapshots collected by `py -3 src\generate_weekly_schedule_report.py --collect` (S first; add `--include-a` for A). JSON schema version 2: `windows[YYYY-MM-DD][normalized_profile_url]` contains `profile_url`, `fetched_at` (JST ISO timestamp), `days` (seven `{date, state, text}` objects), and `error`. The window starts today in Japan and ends six days later. Version 1 `weeks` snapshots are migrated in memory under their original start dates and saved as v2 on collection; offline loading never rewrites them. Only an exact start-date/seven-date match is used, never shifted or filled from another window. States are `working`, `off`, `undecided`, `unpublished`, `unknown`, or `error`; missing snapshots are displayed as `not_fetched`, never off. Atomic replacement preserves other windows and unselected people. Display filters (working within seven days by default, today, weekend, or all) do not change ranking or collection selection. Unlike the legacy calendar/profile cache, this file is separate so daily unknown/error states do not change the existing weekend calendar or joins. Commit it after an intentional collection if the published HTML should retain the snapshot across environments; no live collection is needed for offline generation.

- `tokai_fuzoku_reports.jsonl`: collected Tokai Fuzoku reports, one row per article (`url`, normalized to `https://m.fuzoku-tokai.com/YYYY/MM/DD/post-N/`). Generated by `src/tokai_fuzoku/collect_fuzoku_tokai.py` and read by `src/tokai_fuzoku/generate_report_final.py`. The generated page groups these article rows for display by normalized `girl_url` without changing the JSONL; both 返す and 返さない reports remain available under each person. A person is identified at runtime by the normalized `girl_url` (CityHeaven URLs are cut to `.../girlid-N/`, tracking parameters are dropped, identifying query parameters such as `?id=` are kept); rows are never merged by shop + name, and changed URLs or shop moves are not merged by guesswork.
  Rows written by the new collector also store the report details: `total_point`, `style_score`, `play_score`, `panel_score` and the comment columns (`total_comment`, `face_comment`, `style_comment`, `play_comment`, `panel_comment`, `bust_comment`, `repeat_comment`), `play_time`, `total_cost`, plus `profile_status` (`published` / `unavailable` / `unknown`), `profile_checked_at` and `fetched_at`. Missing values stay `null` (never 0). Older rows without these keys stay valid and are not rewritten unless they are updated.
  Re-fetching an article only fills empty fields: `delete?`, manual corrections and existing values are kept.
  Run from `src/tokai_fuzoku` (requires `FUZOKU_TOKAI_PASSWORD`):
  - `python collect_fuzoku_tokai.py`: normal incremental run. Re-reads the listing from (newest `date` − `--overlap-days`, default 3) so same-day or slightly late posts are not missed, and fetches only article URLs not yet stored. Articles added later with older dates are not guaranteed to be caught; use the backfill for those.
  - `python collect_fuzoku_tokai.py --backfill [--resume] [--limit N] [--max-pages N]`: pages through the whole listing without the date cutoff and fetches only unstored articles. Progress is saved every page/10 articles, so an interrupted run continues with `--resume`. `--max-pages` (default `FUZOKU_TOKAI_MAX_PAGES` or 75) and `--limit` (articles fetched) cap a run.
  - `python collect_fuzoku_tokai.py --fill-details [--limit N]`: fetches stored articles that have no `fetched_at` and fills only missing detail columns (no profile check).
  - `python collect_fuzoku_tokai.py --recheck-profiles [--status unavailable|unknown|published ...] [--limit N]`: re-judges the stored `profile_status` of people whose latest status matches `--status` (default `unavailable`; repeatable), once per person, without login or password. Only a definitive new result (`published` / `unavailable`) updates that person's rows; `unknown` leaves them as they are. It rewrites the JSONL, so do not run it while another collection run is in progress.
  Each run prints added / updated / unchanged / non-report / failed counts. Profile pages are checked once per person per run. `unavailable` needs clear evidence: HTTP 404/410, a redirect to a different page, or a site-specific empty profile template (shaboole title `｜[]プロフィール`, stylish-bach girldetail pages without profile elements). A CityHeaven `girlid-N` page returning 200 at the same URL is `published` without a name check. Other sites are `published` when the name matches after removing rank tags (`【…】`, `[…]` etc.) and symbols (♡☆★♪…), with `名前（読み）` matching on the main name; a name mismatch alone, 403/429/5xx, timeouts and browser failures are `unknown` (not treated as removed). A login page stops the run instead of being recorded.
- `tokai_fuzoku_collect_state.json`: local collector state (non-report article URLs, failed URLs to retry, backfill resume page); excluded from Git. Delete it to re-check non-report articles or restart a backfill from page 1.
- `python generate_report_final.py` (from `src/tokai_fuzoku`) builds `docs/tokai_final_report.html` with the existing online checks (login, profile availability, profile images) and fetches details only for rows without stored details. `python generate_report_final.py --offline` needs no password or network: it uses stored details only and skips profile re-checks and images. Both exclude people whose latest stored `profile_status` is `unavailable`; the online profile check uses the same evidence rules as the collector (name mismatch or request failure keeps the row). 返さない reports are now shown too; use the page's リピート filter to narrow them.
- `tokai_fuzoku_report_history.jsonl`: extracted report history used to match reports with CityHeaven profiles. Updated by `src/integrations/report_left_merge.py`. `evaluations` is a JSON object. New reports are detected by normalized article URL (`report_url`), so a person's later reports are added as separate rows and the same article is never added twice.
  Extraction reads each nested `article-entry` in the grouped Tokai page, with the profile link from its enclosing person and scores/comments from that article only. Legacy ungrouped pages are also supported.
  The calendar keeps Tokai rows per article and groups Okinilove articles into a per-profile list before joining, preventing a Tokai-count × Okinilove-count Cartesian product. Every article in both sources is displayed, including different articles with identical comments and Okinilove review fragments from the same page. Missing profile keys never match other missing keys. Duplicate normalized CityHeaven calendar profile keys raise a merge error rather than silently discarding rows. Runtime performs no content-based deduplication or persisted-data cleanup.
  The checked-in history was repaired once from the saved article-level Tokai HTML: 280 URL-less person aggregates were replaced by their source articles after checking every nonempty score/comment against those articles. The 226 existing URL-bearing rows were retained unchanged, with 310 missing article rows added. Existing unambiguous CityHeaven enrichment was retained by normalized profile URL (including identifying query parameters for external sites); no name-based matching was used. This is source reconstruction, not deduplication by comment text.
- `okinilove_reviews.jsonl`: Okinilove review records, maintained by `src/okinilove/okinilove_left_merge.py`; includes `face`, `service`, and `age` details when available, with face/service supplemented from `okinilove_report_details.json`.
- `okinilove_shop_index.json`: cached shop index (shop name -> 全投稿履歴 URL) built from Okinilove category pages (categories 70–72: デリヘル・ヘルス・ソープランド); refreshed every 7 days. Review scraping excludes shops identified as ぽっちゃり系 by their name or category industry label, and category 70 also excludes shops with age-related terms in the name or category-70 industry label. The generated people-review HTML hides ぽっちゃり系 shops by default and provides a checkbox to show them.
  `report_left_merge.py` only re-links rows with an empty `cityheaven_url` by matching shop + name against people on the CityHeaven calendar (no network). The slow maintenance steps are off by default and run separately with `python okinilove/maintain_okinilove.py --check-unavailable` (HTTP 404/410 removal check, including the `nagoya-choku0930.jp` profile URLs that redirect to the site's verified landing page with no personal data) and/or `--enrich [--time-budget SECONDS]` (shop-page search via `src/ns_senmon/match_cityheaven.py`, prioritising shops on the calendar), or inside `report_left_merge.py` with `OKINILOVE_CHECK_UNAVAILABLE=1` / `OKINILOVE_SEARCH_ENRICH=1`.
- `okinilove_cityheaven_enrich_cache.json`: `"shop_name\tgirl_name"` -> `{checked_at, url}` for the search-based re-linking above; unresolved pairs are retried after 7 days. Committed by the scrape workflow so the retry window survives between runs.
- `okinilove_profile_status.json`: generated 7-day profile status cache; excluded from Git. Cached results are reused until they expire, independently of new-review collection; timeouts and connection failures are not cached and are retried on the next run. When the removal check runs, people shown on the CityHeaven calendar (`data/cityheaven_profiles.json`, if present) are treated as still listed and are not checked.
- An Okinilove article can be checked directly for numbered-www profile links without crawling shop histories or retrying the skipped-article cache: `python src/okinilove/scrape_okinilove.py --recover-numbered-profile-article "https://okinilove.com/blog-entry-2811.html"`. This reads only the specified article, checks only unregistered numbered-www profile links it contains against the corresponding `www.` host, then adds confirmed reviews through the normal JSONL/HTML flow.
- `ns_senmon_profile_image_cache.json`: `cityheaven_url` -> `{checked_at, status, image_url, shop_checked, shop_kind, price_class}` for the CityHeaven profile photos and shop type shown in `docs/ns_senmon_report.html`. `shop_kind` is the text after the shop name in the profile page's `.shopname` (e.g. `ソープ(高級/金津園)`) and `price_class` is its price tier (`高級` / `スタンダード` / `大衆` / ... or empty); the page's 店舗種別 filter treats `高級` as luxury and everything else as 高級以外, while people without these keys (not linked or not fetched) appear only under すべて. Written by `src/ns_senmon/profile_images.py` when `src/ns_senmon/generate_ns_senmon_report.py` runs. `ok` entries are refreshed after 90 days (entries without `shop_checked` are re-fetched immediately), `no_image` / `error` are retried after 7 days, and `not_found` (HTTP 404/410) is never re-fetched. Fetching is capped at 120 seconds per run; failures leave the person without a photo. Commit it together with the regenerated HTML.

Published pages in `docs/` share `docs/common.css` (static, edited by hand; dark mode and iPhone/safe-area rules) and `src/web_common.py` (shared head, 「← 一覧」 nav, 「先頭へ」 button). `src/okinilove/render_people_summary.py` writes the review bodies (face/style/service/text) to `docs/okinilove_review_bodies.json`, which the people-review page fetches when a person is opened; review links, ratings, and gaps stay in the HTML because the scrapers re-parse it.
People-review positive/negative rates count reviews containing at least one corresponding face, photo-gap, or style item, divided by reviews containing a recognized positive, negative, or neutral item. Mixed reviews count toward both rates; unknown/unclassifiable-only reviews are excluded. Counts for positive-only, mixed, negative-only, and neutral-only reviews are displayed. Photo matches are positive, youthful appearance is neutral, and style `ナイスボディ` is positive. `ぽっちゃり` and `おなかぽっこり` (including `お腹` / `ポッコリ` spelling variants) are negative according to the selected preferences, not universal judgments; `デブ` and `ちょいぽちゃ` remain neutral pending explicit classification changes. Unknown values, including misplaced face `ナイスボディ`, do not contribute to the denominator.
Service items also contribute to these review-level rates and the recommendation score. Positive service items are `フェラ上手`, `キス上手`, `一生懸命`, `テクニシャン`, `手コキ上手`, and `いちゃいちゃ`; negative items are `事務的`, `サバサバ`, `手抜き`, and `地雷`. Other recognized service items, including `ぎこちない`, are neutral. Service-only reviews with recognized items are eligible; multiple positive or negative items still count only once per review. SP service filtering accepts both `SP` and `SP（スペシャルサービス）`.
Default recommendation sorting compares corrected average stars rounded to one decimal (descending), corrected negative rate (ascending), corrected positive rate (descending), then eligible review count (descending). Stars are corrected by adding three reviews at the global star-rated-review-weighted average; rates are corrected with three reviews at the corresponding global eligible-review-weighted rate. Global baselines include all people on the page and do not change with filters. People without star ratings sort last in recommendation mode; within a star bucket, people without eligible item evaluations follow those with evaluations. Raw positive/negative sorting uses eligible review count then stars and places people without eligible reviews last; average-star sorting uses star-rated count then eligible count. Count sorting uses eligible count then stars. The three-review correction and one-decimal buckets are heuristics, not calibrated confidence estimates. Style and service body entries use `[text, tone]` pairs; the page also accepts legacy strings.

Do not add derived join keys such as `url_key` to the persisted records. Compute them at runtime.
